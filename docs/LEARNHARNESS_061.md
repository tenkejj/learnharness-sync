# LearnHarness 0.6.1 on Linux x86_64

**Historical qualification, November 17.** The later managed run includes an ordinary-UID migration, real ENOSPC, kernel writer refusal and native application checkout tracking. [Current report](MANAGED_LINUX.md)

The checked-in desktop build refuses all production profile operations. Its separate QA peer can synchronize a narrowly validated subset of files generated by the pinned LearnHarness desktop. Tests ran on one Linux host on 2026-11-17. Only disposable profiles were opened.

## Installation and isolation

The local desktop entry invokes a launcher that selects the latest LearnHarness AppImage in the user's Applications directory. The selected 0.6.1 x86_64 binary matched the upstream release digest `b8a033eb7421677893d96e4988b30153fdfe4fc6f0dc456f7947161bba041b98`. The QA runner checks a private copy before extracting it. The release tag resolves to commit `cb25c8e49b85eed9e78315584731cad73a0118a6`. [Release](https://github.com/amosblomqvist/learnharness/releases/tag/v0.6.1) · [Tagged source](https://github.com/amosblomqvist/learnharness/tree/cb25c8e49b85eed9e78315584731cad73a0118a6)

Run from a Linux checkout with the locked npm dependencies, Rust, bubblewrap, Xvfb, curl and GNU coreutils with exchange support. The optional second argument selects an Xvfb binary. The official LearnHarness distribution is supplied locally.

```sh
scripts/test-learnharness-desktop ~/Applications/LearnHarness-0.6.1-x86_64.AppImage
```

Every launch gets private PID, mount, IPC and network namespaces, fresh environment variables, a private X server, a synthetic home and private XDG directories. The only writable profile mounted into Electron is the current test profile. The host home, network, display, sockets and credentials are absent. The app reads its own release files and the host's read-only system libraries. Tests drive the packaged Electron window's same-origin application requests. The desktop itself supplies its per-launch request capability. No capability or provider key is read by the test. A deterministic keyless loopback model supplies text and structured extraction responses through the normal custom-provider setup flow.

## Persistence contract and adapter boundary

| Store | Evidence and transfer decision |
|---|---|
| Sessions | The packaged application wrote `data/chats/chat_<time>_<nonce>.json` with **version 2**, ID, title, ISO creation/update times and native messages. Practice adds a kind field. A rename preserves updatedAt. Unstamped upstream records denote v1. The QA adapter accepts only the exercised v2 shapes, checks filename/ID identity and transfers original bytes. [Chat contract](https://github.com/amosblomqvist/learnharness/blob/v0.6.1/src/core/contracts/chat.ts) |
| Messages and usage | The generated text turns contain stable user and assistant message IDs. Assistant records include typed text blocks, usage, model and stop information. Turn entries link to assistant IDs. The adapter checks those links and limits assistant/provider settings to the isolated custom test model. Tools, images, side conversations, arbitrary provider records and future fields refuse the operation. |
| Graph | The extraction pipeline wrote format version 1, append-ordered nodes, chains and coverage JSONL plus positions JSON. Chains refer to premises and conclusion by node ID. Node provenance refers to chat and message IDs. A chain can have a chat-level anchor with an empty message ID. The validator checks these references, coverage chat and fingerprint shape, layout node IDs and complete inventory for the tested graph family. Duplicate node histories, imported notes and other graph families are outside this subset. [Ledger implementation](https://github.com/amosblomqvist/learnharness/blob/v0.6.1/src/store/graph.ts) |
| Graph versions and migrations | Upstream treats a missing graph stamp as legacy v1. Future formats require refusal. QA requires an explicit graph stamp when graph files are present. Coverage fingerprints and original ledger order travel unchanged. Semantic replay of arbitrary historical operations and downgrade migration are unqualified. |
| Jobs and extensions | Jobs reference chat and tool-call IDs, carry status and may represent active work. Even a terminal job can contain paths or private inputs. Empty jobs/plugins directories occur on first use. Any entries in them, project metadata outside the allowlist, model caches, debug logs, prompt overrides, themes or unknown inventory block this QA transfer. [Store configuration](https://github.com/amosblomqvist/learnharness/blob/v0.6.1/config.ts) |
| Settings, accounts and runtime | A keyless setup wrote the local endpoint and credential binding ID in settings.json. Settings remain device-local during staging. Both rich test profiles independently configured the same mock service. Auth files outside data, the Electron profile and all provider credentials are outside the transfer roots. Arbitrary settings or equivalence of independently configured real providers have no production certification. |
| Files and notes | LearnHarness supports machine-local file references. Imported notes have path-derived source identity, separate provenance and usage. Image snapshots and attachment-bearing variants need their own portability and recovery contract. The 0.6.1 composer embeds quoted local paths in ordinary message text. The QA adapter refuses path separators even in plain text, including benign fractions and URLs. An isolated paste of a real disposable file path exercised this refusal after persistence. Free-form user text can itself contain sensitive information. [Upstream usage and attachment behavior](https://github.com/amosblomqvist/learnharness/tree/v0.6.1) |

## Exclusion, transfer and recovery

LearnHarness starts a separate server with the Electron data directory. Its single-instance lock coordinates compatible Electron launches. The per-file JSON writer fsyncs a temporary file and renames it. The graph writer appends JSONL and rewrites individual ledgers. The upstream reader can skip malformed JSONL. LearnHarness Sync rejects malformed transferred records. These stores have no shared cross-file write lock or snapshot transaction. A standalone server can address the same data path independently. Closing a window, checking process names, taking a LearnHarness Sync-only lock or comparing mtimes cannot prevent a later writer. [Electron lifecycle](https://github.com/amosblomqvist/learnharness/blob/v0.6.1/electron/main.cjs) · [Atomic writer](https://github.com/amosblomqvist/learnharness/blob/v0.6.1/src/store/atomic-write.ts)

In QA, the runner alone creates and launches these profiles. It waits for the namespace to exit before inventory, staging or replacement. An app still running or a launch timeout aborts that test sequence. Two independent peers validate bounded inventories and exchange immutable objects through the existing pinned QUIC connection. QA manifests have a distinct format. The release binary does not enable the QA feature. The origin and receiver compare file bytes, verify adoption and wait for application readback. Repeat publishing returns the same head.

The runner checks the destination against the expected previous content, preserves local settings, builds a sibling directory and flushes the filesystem. Linux directory exchange activates the entire tree at once. The fault test kills the test committer immediately after exchange, reverses the exchange, compares the restored tree against an independent copy and reapplies. The app then opens the result. These backups live for the duration of the disposable test. The engine separately stores backups and conflict branches. Production crash recovery, a durable journal across arbitrary machine restarts, actual ENOSPC and power-loss testing remain open.

## Observed acceptance

- **A and B** created and reopened teach/practice sessions. Six IDs survived both directions, including Unicode titles, larger records and successive renames. A model-less session returned HTTP 503 with `models_not_configured`.
- **C and D** exercised two user turns and two assistant replies, usage records, extraction, two propositions, a reasoning chain, positions, coverage and chat/message provenance. The installed application reopened the graph and transcript on D, renamed the chat offline and read the changed title on C after reverse sync.
- Both peers then authored distinct closed-profile revisions. After reconnect, each retained its own head and could retrieve both complete branches. Corrupt JSON/JSONL, missing graph data, invalid endpoints, new schemas, unknown fields and unsafe paths were refused. No records from an owner profile entered a test.
- Physical LAN operation of this exact candidate and real-data operations outside the namespace were not exercised. No production LearnHarness version has qualified.

## Candidate builds and release gates

The private AppImage passed the packaged UI/native smoke on the development host. The DEB installed using APT/dpkg in an isolated Ubuntu 24.04.5 filesystem and the RPM using DNF/RPM in Fedora 44. Final packages were reinstalled and relaunched under unprivileged accounts, preserving generated device identity bytes. The toolchain remaps developer paths. The AppImage passed both direct and extract-and-run launches. All three bundles passed extraction and targeted credential and runtime checks. The packages include the Manrope font license, project license and notice. The artifact hashes are in the local bundle's SHA256SUMS.

All 487 locked Cargo metadata packages declare a license expression. RustSec database commit `233155b4025b854c68a4b199c0e32d7fd53291a2` reported zero vulnerabilities, two unmaintained advisories (chrono and proc-macro-error) and an unsoundness warning for glib. npm audit found zero production findings and four high development-tree entries tracing to picomatch 4.0.7. Transitive notice obligations, bundled native-library redistribution and artwork rights remain open. The separate upstream AGPL project and test AppImage are not vendored. [npm advisory](https://github.com/advisories/GHSA-fc5q-39xc-vjpf) · [glib advisory](https://rustsec.org/advisories/RUSTSEC-2024-0429.html)
